# Нестабильный HudUpdateDoesNotAllocate — проект исправления
## 1. Первопричина
Лишнее выделение — шум редактора, а не код HUD. Доказательства (временные пробы, в репозиторий не вошли):
- Окно с пустым делегатом `() => { }` получило лишний GC.Alloc в 4 из 7 сбойных окон первой пробы. Код главного потока в таком окне ничего не выделяет.
- В 100 000 окнах с циклом сложения float без выделений глобальный счётчик `GC Allocation In Frame Count` (`ProfilerRecorder`, все потоки) насчитал 248 выделений в 76 окнах: их делают фоновые потоки редактора. `Recorder("GC.Alloc")` с `FilterToCurrentThread` засчитал одно такое выделение окну главного потока (в этом окне счётчик показал 7 выделений, 364 байта).
- Сбои приходят в случайных кадрах, иногда пачкой из 2–3 соседних окон (в одном из окон счётчик всех потоков показал 321 выделение); повтор того же детерминированного сценария (seed 7) сразу после этого чистый. В 5 запусках редактора по 40 повторов сценария шумный прогон был не больше одного за запуск.
- `Profiler.GetMonoUsedSizeLong` растёт в окнах, где Recorder насчитал 0: фоновые потоки выделяют память параллельно с тестом.
Изредка лишний сэмпл приходит и при нуле по счётчику всех потоков; источник внутри профайлера редактора не установлен, но он одинаково появляется и в окне пустого делегата, то есть не связан с кодом HUD.
`GC.GetAllocatedBytesForCurrentThread` в Mono редактора всегда возвращает 0 (в пробе 0 и для окон с двумя настоящими выделениями), поэтому заменить Recorder точным счётчиком потока нельзя.
Код игры не меняется: в плеере HUD выделяет 0 байт (§4).
## 2. Исправление теста
Сценарий детерминирован (seed 7, фиксированный шаг, одинаковые надписи), поэтому выделение кода HUD повторяется в том же окне каждого прогона, а шум — нет.
- `HudAllocationScenario()` — прежний сценарий (60 кадров прогрева, 300 кадров замера без босса, 30 кадров прогрева с боссом, 300 кадров замера с боссом, те же проверки числа изменений). Возвращает окна, где число выделений отличается от ожидаемого, с ключом «фаза/кадр/вид окна». Меньше 2 выделений на изменившуюся надпись — немедленный провал (это детерминированно).
- `HudUpdateDoesNotAllocate` выполняет сценарий до `MaxScenarioRuns` = 3 раз: чистый прогон завершает проверку; окно, отклонившееся в двух прогонах, — провал с контекстом всех прогонов. Если шум был, а повторов нет, тест пишет `Debug.Log` с контекстом.
- `HudUpdateWithoutChangesDoesNotAllocate` повторяет одно и то же окно (состояние не меняется) до 3 раз, провал — если выделение в каждом.
- Контекст окна дополнен числом выделений всех потоков (`GC Allocation In Frame Count`), чтобы по сообщению было видно фоновую активность.
- Проверка мутантом: временное однократное `new object()` в `UpdateHud` на 15-й секунде дало провал «allocation repeats in the same window of two runs» в кадре `boss frame 59` обоих прогонов.
## 3. Почему не ослабление
- Выделение в коде HUD каждый кадр или однократно в любом кадре ловится, как и раньше: оно повторяется в следующем прогоне.
- Допуск в 2 выделения на надпись не изменился.
- Не ловится только выделение, которое в коде HUD происходит недетерминированно и не повторяется ни в одном из трёх прогонов в том же кадре. В коде HUD таких источников нет (ни времени, ни случайности, ни потоков).
## 4. Замер в плеере
- Ключ `-thornHudAlloc` (только вместе с `-thornSmoke`): `HudAllocMeter` с 5 до 25 с времени забега оборачивает каждый `GameUi.UpdateHud` и следующий за ним `Canvas.ForceUpdateCanvases` (перестройка сетки TMP изменившихся надписей; обычная перестройка перед отрисовкой после этого ничего не находит). Без ключа кадр не меняется.
- В каждом окне суммируются три счётчика: `ProfilerRecorder` «GC Allocated In Frame» (байты, все потоки), `GC.GetAllocatedBytesForCurrentThread`, `Profiler.GetMonoUsedSizeLong`. Калибровка в конце: столько же окон с `new byte[16]`. Метод отчёта — первый счётчик, у которого калибровка больше 0.
- Число изменений надписей — `GameUi.HudTextChanges` (сумма `HudText.Set`, вернувших `true`). `label.text` в плеере не читается: геттер TMP может собрать строку.
- `MobileBuilder.BuildMacSmoke` с `-thornRelease` собирает плеер без Development Build в `Builds/MacRelease`. `Tools/mac-smoke.sh --hud-alloc` собирает его и проверяет строку, код 11 при ошибке.
- Точность. В release-плеере Mono нет ни счётчика профайлера (`counter_valid=0`), ни счётчика потока (калибровка 0), поэтому метод — `mono_heap`: куча Mono растёт блоками по 4 КБ, и мелкое выделение видно только когда в окне берётся новый блок. Калибровка 1198 окон по 48 байт дала 73 728 байт (18 блоков), то есть метод видит выделения такого порядка. Точный замер даёт Development-плеер (`Tools/mac-smoke.sh -thornHudAlloc`, метод `profiler_counter`): калибровка 1194 × 48 = 57 312 байт совпала байт в байт.
- Результат (2026-11-11): release — `bytes=0 canvas=0 frames=1198 changes=41 method=mono_heap calibration=73728` и повторно `bytes=0 canvas=0 frames=1192 changes=44 calibration=77824`; Development — `bytes=0 canvas=0 frames=1194 changes=41 method=profiler_counter calibration=57312`. Меняются время и убийства; уровень в 30-секундном smoke без ввода не растёт, фаза босса в плеере не замерялась (её покрывает EditMode-тест).
## 5. Риски
- Нестабильность фоновых потоков редактора может дать шум в трёх прогонах подряд в одном и том же окне — тогда тест упадёт ложно. Вероятность оценена как очень малая (сбойных окон 1–3 на 1200, совпадение кадра в двух прогонах ~0,3 % при условии шума в обоих).
- `Canvas.ForceUpdateCanvases` в режиме `-thornHudAlloc` выполняет перестройку раньше обычного; это только диагностический режим smoke.
- В release-плеере замер грубый (блоки 4 КБ); отсутствие выделений подтверждает точный счётчик Development-плеера с тем же кодом HUD.
