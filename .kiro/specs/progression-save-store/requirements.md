# Требования: сохранения, сборка ThornThrone.Progression (Task 12)

Источник: `.kiro/steering/roadmap.md`, Task 12 и раздел «Архитектура»; `ТЗ_Мобильная_версия_v2.md` §8 (слои App/Data/Simulation/Presentation/Input/UI/Platform), §9 (жизненный цикл и сохранения), §12 (воспроизводимость, проверки); `product.md` («Не входит в объём»: сохранение незавершённого забега, облако).

Сейчас постоянного состояния нет: ни `PlayerPrefs`, ни файлов в `persistentDataPath`. Валюта, улучшения, открытия, результаты и настройки появятся в задачах 13, 16, 30–33; эта задача даёт им модель профиля и надёжное хранилище.

Термины:
- **Профиль** — постоянное состояние игрока одного вида (`user` или `test`).
- **Основной файл**, **резервный файл**, **временный файл** — `<вид>.save`, `<вид>.save.bak`, `<вид>.save.tmp` в каталоге сохранений.
- **Целый файл** — файл с верным заголовком, совпадающими длиной и контрольной суммой содержимого и профилем, прошедшим проверку полей.
- **Подтверждённое сохранение** — вызов `Save`, вернувший успех.

## Требования

### 1. Сборка ThornThrone.Progression
1.1. СИСТЕМА ДОЛЖНА содержать сборку `ThornThrone.Progression` (`UnityProject/Assets/Game/Scripts/Progression/`, asmdef с `noEngineReferences: true`, namespace `ThornThrone.Progression`) без ссылок на `UnityEngine` и на `ThornThrone.Simulation`. Из внешних библиотек допускается только `Newtonsoft.Json` (уже подключён в Unity и в dotnet-проекте симуляции).
1.2. СИСТЕМА ДОЛЖНА компилировать исходники сборки вне Unity проектом `DotNet/ThornThrone.Progression/ThornThrone.Progression.csproj` (netstandard2.1, C# 9, `TreatWarningsAsErrors`, без своих .cs файлов), а тесты — запускаться той же командой `dotnet test DotNet/ThornThrone.Simulation.Tests`.
1.3. Сборка `ThornThrone.Mobile` ДОЛЖНА ссылаться на `ThornThrone.Progression`; симуляция не меняется.

### 2. Профиль
2.1. СИСТЕМА ДОЛЖНА хранить в профиле: версию схемы, версию правил, вид профиля, валюту, уровни постоянных улучшений по имени атрибута, открытия, результаты забегов, настройки и журнал применённых наград и покупок.
2.2. КОГДА создаётся новый профиль, СИСТЕМА ДОЛЖНА заполнить его текущей версией схемы и правил, нулевой валютой, пустыми улучшениями, открытиями, результатами и журналом и настройками по умолчанию (таблица в `design.md`).
2.3. КОГДА в журнал добавляется идентификатор операции, который уже есть в журнале, СИСТЕМА ДОЛЖНА вернуть «уже применено» и не менять журнал (§9 «одна награда/покупка применяется один раз»).
2.4. Незавершённый забег в профиль не входит (§9).

### 3. Формат файла
3.1. СИСТЕМА ДОЛЖНА записывать файл как заголовок `THORNSAVE 1 <длина> <sha256>` и перевод строки, за ним профиль в JSON (UTF-8). Длина и SHA-256 считаются по байтам JSON.
3.2. КОГДА заголовок неверен, длина или контрольная сумма не совпадают, JSON не разбирается, отсутствует обязательное поле, встречается неизвестное поле, тип или значение недопустимы (отрицательная валюта или уровень, неизвестный вид профиля, повтор в журнале), СИСТЕМА ДОЛЖНА считать файл повреждённым с диагностикой (какой файл, какая проверка, какое поле). Отсутствующее поле не заменяется нулём или значением по умолчанию.
3.3. КОГДА профиль записан и снова прочитан, СИСТЕМА ДОЛЖНА получить равный профиль (round-trip всех полей).

### 4. Запись
4.1. КОГДА вызывается `Save(profile)`, СИСТЕМА ДОЛЖНА: записать временный файл со сбросом на диск; прочитать его и проверить как целый; если основной файл целый — сделать его резервным; переименовать временный файл в основной. Успех возвращается только после последнего шага.
4.2. КОГДА основной файл повреждён, СИСТЕМА ДОЛЖНА не заменять им резервный: целый резервный остаётся, повреждённый основной переносится в файл диагностики (п. 6.1).
4.3. КОГДА запись или проверка временного файла не удалась (нет места, ошибка ввода-вывода, расхождение суммы), СИСТЕМА ДОЛЖНА вернуть неуспех с причиной, не трогать основной и резервный файлы, удалить временный файл при возможности и не бросать исключение вызывающему коду.
4.4. КОГДА запись прервана на любом шаге (сбой процесса), СИСТЕМА ДОЛЖНА при следующей загрузке получить либо профиль последнего подтверждённого сохранения, либо профиль из сохранения, которое прерывалось; повреждённый или пустой профиль не загружается, если до этого было хотя бы одно подтверждённое сохранение.
4.5. Сохранение вызывает код App (покупка, подтверждение награды, конец забега, изменение настроек — задачи 13, 16, 30–33); `SaveStore` не зависит от callback завершения процесса.

### 5. Загрузка и восстановление
5.1. КОГДА основной файл целый, СИСТЕМА ДОЛЖНА загрузить его (статус `Loaded`).
5.2. КОГДА основного файла нет или он повреждён, а резервный целый, СИСТЕМА ДОЛЖНА загрузить резервный (статус `RestoredFromBackup`) и сохранить повреждённый основной для диагностики.
5.3. КОГДА повреждены оба файла (или повреждён один, а другого нет), СИСТЕМА ДОЛЖНА создать новый профиль (статус `ResetAfterCorruption`), сохранить все повреждённые файлы для диагностики и вернуть их список, чтобы UI показал понятное сообщение.
5.4. КОГДА файлов профиля нет, СИСТЕМА ДОЛЖНА создать новый профиль (статус `Created`) без сообщения.
5.5. КОГДА при загрузке найден временный файл, СИСТЕМА ДОЛЖНА удалить его, кроме случая, когда нет ни основного, ни резервного файла, а временный целый: тогда он становится основным.

### 6. Повреждённые файлы
6.1. СИСТЕМА ДОЛЖНА переименовывать повреждённый файл в `<имя>.corrupt<N>`, где N — наименьшее свободное число от 1. Файлы диагностики не перезаписываются и не удаляются.

### 7. Версии схемы и правил
7.1. КОГДА версия схемы файла меньше текущей и есть цепочка миграций до текущей, СИСТЕМА ДОЛЖНА применить миграции по порядку и загрузить профиль (статус `Migrated`); исходный файл остаётся основным до следующего подтверждённого сохранения.
7.2. КОГДА версия схемы меньше минимальной поддерживаемой или для неё нет миграции, СИСТЕМА ДОЛЖНА считать файл повреждённым по п. 3.2 (рекорды прототипа автоматически не переносятся, §9).
7.3. КОГДА версия схемы больше текущей (установлен более старый APK), СИСТЕМА ДОЛЖНА поступить как с повреждённым файлом: сохранить его для диагностики, не перезаписывая.
7.4. КОГДА версия правил в профиле отличается от текущей, СИСТЕМА ДОЛЖНА загрузить профиль без изменений. Каждый результат хранит версию правил, на которых он получен; сравнимость рекордов решает задача 32.

### 8. Профили user и test
8.1. СИСТЕМА ДОЛЖНА хранить профили `user` и `test` в разных файлах; запись и восстановление одного не читают, не меняют и не удаляют файлы другого.
8.2. Выбор профиля при запуске (`-thornProfile=test`) и содержимое тестового профиля — задача 32.

### 9. Файловая система
9.1. СИСТЕМА ДОЛЖНА работать с файлами только через интерфейс `IFileSystem` (существование, чтение, запись со сбросом на диск, переименование, удаление).
9.2. СИСТЕМА ДОЛЖНА содержать `DiskFileSystem` поверх `System.IO`, ограниченную корневым каталогом: имена файлов без разделителей пути и `..`.
9.3. СИСТЕМА ДОЛЖНА содержать в слое Platform Unity (`Scripts/Mobile/Platform/`) обёртку, которая открывает `SaveStore` для вида профиля в каталоге `Application.persistentDataPath/Saves`.

## Критерии приёмки
- dotnet-тесты с фейковой ФС: round-trip; порча основного (восстановление из резервного); порча обоих (новый профиль, повреждённые файлы сохранены); прерванная запись на каждом шаге `Save`; нет места; старая схема (миграция и неподдерживаемая); новее текущей; отсутствующее обязательное поле; идемпотентный журнал; изоляция `user`/`test`.
- dotnet-тесты `DiskFileSystem` на временном каталоге: round-trip и отказ от имени с путём.
- EditMode-тест: обёртка Platform указывает на `persistentDataPath/Saves`.
- `dotnet test DotNet/ThornThrone.Simulation.Tests` и `Tools/unity-tests.sh` зелёные; Unity компилирует новую сборку (smoke `Tools/mac-smoke.sh` проходит).
