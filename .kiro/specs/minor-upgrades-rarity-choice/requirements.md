# Требования: малые улучшения, редкость, правила выбора (Task 26)

## Введение
Сейчас способность на максимальном ранге выпадает из выбора: `Build.CanUpgrade` возвращает ложь при `Rank == MaxLevel`, поэтому `m_vecMinorUpgradeChoices` активных способностей не применяется нигде (Mechanics §15, §26, §32 «Не сделано»). Когда кандидатов нет, игрок получает придуманное лечение +30 HP (`Rules.FallbackHeal`, Differences A19). Карточка (`GameUi.Describe`) показывает только прибавку записи («+5 Магический урон»), а не значение «было → станет», и ничего не говорит о редкости.

Задача: малые улучшения после максимума, редкость в данных выбора и на карточке, явные правила при заполненных слотах, запасная награда по клиенту, конкретные изменения на карточке. Финальный вид карточек (иконки, раскладка) — Task 35, здесь только данные выбора и текст текущей карточки.

### Источники
- **Д** `survivors_powerups.json`: у 44 powerups есть `m_vecMinorUpgradeChoices`; у 17 активных способностей 1–3 варианта, только `m_vecUpgradeAttributes`. У всех 52 вариантов `m_unRarity = RARITY_COMMON`; у записей `m_vecAuthoredUpgradeChoices` поля редкости нет. `gold` (ID 999, `m_bIsGold`, `m_bRollable = false`, «Мешочек с золотом»), `pile_of_coal` (ID 1000, `m_bRollable = false`, «Гора угля»); количества золота у powerup `gold` нет. Подбор `gold_bag` — `m_nGoldAmount` 10.
- **Д** (локализация режима): `DOTA_Survivors_PowerupUpgradeDetails` «{attribute_name}: {current} -> {upgraded}», `DOTA_Survivors_MaxLevel` «МАКС.», `DOTA_Survivors_NewPowerup` «Новое», `DOTA_Survivors_LevelUpgradeInfoLong` «Уровень {current} -> {upgraded}».
- **К** (`Research/Decoded/client/strings.json`): `m_vecMinorUpgradeChoices`, `m_vecMinorUpgrades`, `ESurvivorsUpgradeRarity`, `m_eRequiredOfferRarity`, `m_unRarity`, `m_nRollWeight`, `m_bIsGold`, имя `powerups/gold`; имени `pile_of_coal` в коде нет (Mechanics §10). Алгоритмов выбора нет (Mechanics §16).
- Mechanics §4 (редкость, смещение записей), §12.3, §16, §25 Р1–Р2; Differences A19.

## Требования

### Т1. Малые улучшения после максимума
1.1 КОГДА генерируется выбор при уровне и активная способность героя (не врождённая) имеет ранг `MaxLevel` и хотя бы один вариант `m_vecMinorUpgradeChoices`, СИСТЕМА ДОЛЖНА включить её в кандидаты как малое улучшение с весом `m_flExistingItemWeight` (0.35).
1.2 КОГДА способность попадает в список как малое улучшение, СИСТЕМА ДОЛЖНА выбрать один её вариант через `Rng` симуляции (равновероятно) и показать его на карточке; в списке каждая способность встречается не больше одного раза.
1.3 КОГДА игрок выбирает малое улучшение, СИСТЕМА ДОЛЖНА прибавить атрибуты варианта к атрибутам способности (`m_vecUpgradeAttributes` → `Local`, `m_vecGlobalUpgradeAttributes` → `Global`), ранг не меняется; повторный выбор того же варианта суммируется, ограничения числа нет.
1.4 КОГДА вариант малого улучшения прибавляет урон другого типа, чем урон способности (`annihilation`, `snotty_bat`: `Damage_Magical` при `Damage_Physical` в базе), СИСТЕМА ДОЛЖНА применить правило, утверждённое владельцем (design §4, вопрос В2).
1.5 КОГДА способность получила малое улучшение, СИСТЕМА ДОЛЖНА использовать новые значения со следующего применения способности (как при повышении ранга).
1.6 КОГДА пассивный предмет достиг максимума, СИСТЕМА ДОЛЖНА поступать по правилу, утверждённому владельцем (design §3, вопрос В1; предложение — больше не предлагать).
Критерии: способность ранга 9 появляется в выборе; после выбора `Stat` вырос ровно на значение из данных, ранг 9; два выбора — двойная прибавка; для каждой из 17 способностей и каждого варианта прибавка видна в характеристике, которую читает обработчик.

### Т2. Редкость
2.1 КОГДА данные загружаются, СИСТЕМА ДОЛЖНА превратить `m_unRarity` варианта в перечисление `UpgradeRarity`; неизвестное значение — диагностика `data:unknown-rarity:<powerup>:<значение>`, вариант считается обычным.
2.2 КОГДА формируется карточка, СИСТЕМА ДОЛЖНА передать её редкость: для малого улучшения — редкость варианта, для нового предмета и повышения ранга — `Common` (у авторских записей поля нет).
2.3 КОГДА карточка показывается, СИСТЕМА ДОЛЖНА вывести строку редкости («Обычное»).
2.4 КОГДА генерируется выбор, СИСТЕМА ДОЛЖНА не менять вес кандидата по редкости (все варианты обычные, Mechanics §4 Р).
Критерии: все 52 варианта загружаются как `Common` без диагностик; все карточки любого выбора — `Common`; подменённое значение даёт одну диагностику.

### Т3. Заполненные слоты
3.1 КОГДА все активные слоты (`m_nMaxActiveSlots` + `ActiveAbilitySlots`) заняты, СИСТЕМА ДОЛЖНА при уровне предлагать только способности героя: повышение ранга, если ранг ниже максимума, иначе малое улучшение.
3.2 КОГДА все пассивные слоты (`m_nMaxPassiveSlots`) заняты, СИСТЕМА ДОЛЖНА в сундуке предлагать только повышение ранга предметов героя.
3.3 КОГДА рецепт поглотил компоненты, СИСТЕМА ДОЛЖНА считать освободившиеся слоты свободными (как сейчас).
3.4 КОГДА кандидатов меньше `m_nLevelUpChoices`, СИСТЕМА ДОЛЖНА показать столько карточек, сколько кандидатов (патч-нота 1.1, Mechanics §16).
Критерии: 5 способностей не максимальны — в выборе только они; все 5 максимальны — только малые улучшения, запасной награды при уровне нет; Apex добавляет слот — снова есть новые способности; 6 пассивок на максимуме — в сундуке запасная награда.

### Т4. Запасная награда
4.1 КОГДА список вариантов пуст, СИСТЕМА ДОЛЖНА предложить одну карточку powerup `gold` (Rules `FallbackPowerUp` = `"gold"`), без кнопки переброса.
4.2 КОГДА игрок принимает запасную награду, СИСТЕМА ДОЛЖНА прибавить к `Run.Gold` количество, утверждённое владельцем (design §5, вопрос В3; предложение — `m_nGoldAmount` подбора `gold_bag`, 10), не лечить героя и закрыть выбор как обычно.
4.3 КОГДА в данных нет powerup `gold` или подбора-источника количества, СИСТЕМА ДОЛЖНА сообщить диагностику `data:fallback-reward` и не падать (награда 0).
Критерии: забег с исчерпанным выбором в сундуке получает +10 золота, здоровье не меняется; `pile_of_coal` не используется и не предлагается.

### Т5. Конкретные изменения на карточке
5.1 КОГДА генерируется выбор, СИСТЕМА ДОЛЖНА для каждой карточки построить без выделений памяти данные: powerup, вид (`New`, `Rank`, `Minor`), текущий и следующий ранг, индекс варианта, редкость и список изменений `AttributeChange` (атрибут, текущее значение, следующее значение, глобальный или свой).
5.2 КОГДА карточка — повышение ранга активной способности, СИСТЕМА ДОЛЖНА взять изменения из записи, которую применит этот ранг (индекс `rank − AuthoredUpgradeOffset`, §4): текущее значение — `Build.Stat` (свой) или `Build.Global` (глобальный), следующее — текущее плюс прибавка.
5.3 КОГДА карточка — малое улучшение, СИСТЕМА ДОЛЖНА взять изменения из выбранного варианта тем же способом (с учётом правила Т1.4).
5.4 КОГДА карточка — пассивный предмет (новый или повышение), СИСТЕМА ДОЛЖНА показать изменение глобальных атрибутов героя от следующего ранга по §25 Р1–Р2.
5.5 КОГДА карточка — новая активная способность, СИСТЕМА ДОЛЖНА показать «Новое» и описание способности, без списка изменений.
5.6 КОГДА карточка показывается, СИСТЕМА ДОЛЖНА выводить изменения в формате локализации `PowerupUpgradeDetails` («Название: текущее → следующее»), заголовок ранга «Уровень r → r+1», у малого улучшения — «МАКС.»; запасная награда — «Мешочек с золотом, +N золота».
Критерии: Arcane Bolt 1 → 2 у Dragonus — изменения записи 0 (`TargetCount`, `CooldownReductionMultiplier`) с текущими значениями из `Build`; Yasha новая — `MovementSpeed` 280 → 305; малое `Damage_Magical` +5 — текущее → текущее + 5; после выбора фактическое значение совпадает со «следующим» на карточке; генерация выбора в шаге не выделяет память (`StepsDoNotAllocateAfterWarmUp`).

### Т6. Неизменное поведение
6.1 СИСТЕМА ДОЛЖНА ПРОДОЛЖАТЬ при уровне предлагать только активные способности, в сундуке — только пассивные предметы, с весами 0.7 / 0.35 / ×0.6 (§12.3, §25).
6.2 СИСТЕМА ДОЛЖНА ПРОДОЛЖАТЬ собирать рецепты автоматически, не предлагать рецепты и поглощённые компоненты.
6.3 СИСТЕМА ДОЛЖНА ПРОДОЛЖАТЬ применять авторские записи по рангам со смещением §4 и пассивки по §25 Р1–Р2.
6.4 СИСТЕМА ДОЛЖНА ПРОДОЛЖАТЬ останавливать все игровые таймеры на время выбора; переброс тратит `MaxRerolls` и генерирует новый список.
6.5 СИСТЕМА ДОЛЖНА ПРОДОЛЖАТЬ не предлагать врождённые, служебные (`gold`, `pile_of_coal`) и нереализованные powerups.
