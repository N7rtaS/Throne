## 1. Обзор

Unity-слой: текст карточки переезжает из `GameUi.Describe` в чистую функцию `ChoiceText.Format` (`Scripts/Mobile/ChoiceText.cs`) с EditMode-тестами; раскладка карточек не меняется (финальный UI — Task 35).

## 2. Данные

## 3. Правила выбора
Порядок кандидатов прежний (перебор `data.PowerUps.Values`), веса прежние. Изменения:

| # | Правило | Метка |
|---|---|---|
| Р1 | Активная способность (не врождённая) на ранге `MaxLevel` с непустым `Minor` — кандидат «малое улучшение» с весом `m_flExistingItemWeight` 0.35, как у остальных способностей героя | **Р** (`m_vecMinorUpgradeChoices` после максимума — §4, имя поля **К**, вес не найден) |
| Р2 | Одна карточка на способность; вариант выбирается равновероятно `Rng.NextInt(Minor.Length)` сразу после того, как способность вытянута в список. Порядок бросков: бросок веса, затем бросок варианта | **Р** (`m_nRollWeight` **К**, значения нет; все варианты обычные) |
| Р3 | Малые улучшения не ограничены числом; одинаковые варианты суммируются | **Р** |
| Р4 | **Пассивка на максимуме не предлагается** (её ранговый бонус уже и есть первое малое улучшение, §25 Р2; иначе сундук никогда не исчерпается). Утверждено владельцем (В1) | **Р** |
| Р5 | Заполненные слоты: новая способность или предмет не предлагаются, пока свободного слота нет (правило уже есть в `CanUpgrade`, закрепляется тестами). При заполненных и максимальных активных слотах уровень даёт только малые улучшения | **Р** (§16: поведение при заполненных слотах не найдено) |
| Р6 | Редкость не влияет на вес (все варианты `Common`) | **Р** (§4) |
| Р7 | Редкость карточки нового предмета и повышения ранга — `Common` (у авторских записей поля нет) | **Р** |

`Build.CanUpgrade(def)` остаётся «можно повысить ранг или взять» и для максимального ранга возвращает ложь; новый `Build.CanOffer(def, out kind)` добавляет вид `Minor`. `Build.Upgrade(def)` (тесты, `-thornForce`) на максимуме по-прежнему возвращает ложь; для тестов и отладки — `Build.UpgradeMinor(def, index)`.

`Choices` остаётся `List<PowerUpDef>` (API для `MobileGame`, тестов, `Choose(def)`), параллельно — `Offers` (`ChoiceOffer[8]`, заполнено `OfferCount`). `Choose(def)` берёт вид и индекс варианта из своей карточки.

## 4. Урон другого типа в малом улучшении (вопрос В2)
У `annihilation` (`Damage_Physical` 220, описание «физический урон») и `snotty_bat` (`Damage_Physical` 10) малое улучшение — `Damage_Magical` +100 / +2. `AbilityBase` определяет тип урона по базе и читает только свой атрибут, поэтому буквально прибавка ничего не делает.

| Вариант | Поведение | Плюсы / минусы |
|---|---|---|
| **А (утверждён владельцем)** | Прибавка урона другого типа идёт в урон способности её типа: +100 / +2 к `Damage_Physical`. Карточка показывает «Физический урон: 220 → 320» | Просто, карточка честная, обработчики не меняются. Отходит от буквы данных — запись в Differences |
| Б | Буквально: `Damage_Magical` в `Local`, урон не меняется | Верно данным, но карточка Snotty Bat бесполезна (у Annihilation остаются `TargetCount` и сокращение) |
| В | Второй экземпляр урона — магический +100 / +2 в том же попадании (сопротивления, Kaya, врождённая Shen) | Ближе к букве, но меняет `AbilityBase`, статистику и события у двух способностей |

Правило варианта А (**Р**): для способности с известным типом урона (`AbilityBase.DamageTypeKnown`) атрибут `Damage_Physical`/`Damage_Magical` малого улучшения, не совпадающий с типом базы, при применении и на карточке заменяется атрибутом типа базы. Только для малых улучшений; авторские записи не трогаются (в данных расхождений нет).

## 5. Запасная награда (вопрос В3)
- **Что** (**Р** по клиенту): powerup `gold` — его имя и поле `m_bIsGold` есть в коде клиента (**К**), а `pile_of_coal` в коде нет (§10). Придуманное лечение +30 убирается.
- **Сколько** (**Р**, утверждено владельцем): у powerup `gold` количества нет. Берётся `m_nGoldAmount` подбора `gold_bag` = 10 (то же название «Мешочек с золотом»). Число берётся из данных подбора, а не из кода.
- Реализация: `Run.Choose` при `ChoicesAreFallback` вызывает `GrantFallbackReward()` (`Run.Choices.cs`): `Gold += amount`. Переброс в запасной награде недоступен (как сейчас). Золото в профиль — Task 31.
- Нет `gold` или `gold_bag` в данных — диагностика `data:fallback-reward`, награда 0.

## 6. Карточка (`ChoiceOffer`)
```
sealed class ChoiceOffer { PowerUpDef Def; OfferKind Kind; int Rank, NextRank, MinorIndex; UpgradeRarity Rarity;
                           readonly AttributeChange[] Changes = new AttributeChange[8]; int ChangeCount; }
struct AttributeChange { int Attribute; float Current, Next; bool Global; }
enum OfferKind { New, Rank, Minor }
```
Восемь карточек и восемь изменений на карточку создаются в конструкторе `Build`; в шаге только заполняются (наибольшая запись — 5 атрибутов, Snotty Bat запись 8). Переполнение — изменения сверх 8 не показываются, диагностика `build:offer-changes` (не ожидается по данным).

Значения (**Р**, по формуле `Build`: характеристика = `Local` + `Global`):
- Свой атрибут: `Current = Stat(owned, a)`, `Next = Current + value`.
- Глобальный: `Current = Global[a]`, `Next = Current + value`.
- Повторы атрибута в одной записи (Snotty Bat запись 8: урон +5 и +3) сводятся в одно изменение: +8.
- Новая активная — без изменений (описание способности, `LocAbilityDesc`). Новая/повышаемая пассивка — глобальные атрибуты следующего ранга (§25 Р1: запись `rank` у Crystalys, иначе `Minor[0]`).
- Значения — сумма атрибутов, а не итоговая сила после формул (`CooldownReductionMultiplier` 0.05 → 0.10, а не перезарядка в секундах). Так же устроена строка клиента `AttributeUpgradeDetails` для постоянной прокачки (Task 33). Итоговые формулы на карточке — Task 35.

Текст (`ChoiceText.Format`, Unity): название; «Новое» / «Уровень r -> r+1 / max» / «МАКС.»; строка редкости «Обычное»; строки «Название атрибута: 7 -> 12»; у новой способности — описание. Стрелка `->` — как в строках локализации оригинала. При реализации таблицы `GameUi` (суффиксы вида «% опыта») заменены: названия атрибутов — из оригинального `survivors_attributes_russian.txt` (таблица в `ChoiceText`), проценты — по `m_bPercentage` из `survivors_attributes.json` (`GameData.AttributeDefinitions`). `GameUi.Describe`/`Lines` удалены.

## 7. Риски
- Меняется последовательность `Rng` у забегов, где способность достигла максимума (бросок варианта). Тесты от точной последовательности не зависят (проверено на Task 18, §25 Р12).
- `SimulationTests.ChoicesAreDistinctValidAndImplemented` ожидает исчерпания выбора за 44 раунда (теперь выбор при уровне не исчерпывается) и `FallbackWhenNothingIsLeft` — пустой выбор при уровне. Это прежнее поведение, которое задача меняет: тесты переписываются на «пул повышений рангов исчерпывается за N раундов, затем идут только малые улучшения» и «запасная награда — в сундуке при максимальных пассивках».
- Бот-забеги длиннее: при максимумах способности продолжают расти, убийств больше. Пороги в бот-тестах — нижние, не верхние.
