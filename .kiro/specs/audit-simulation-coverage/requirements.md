# Требования: `audit.py` считает покрытие по новой симуляции (Task 5)

Источник: `.kiro/steering/roadmap.md`, Task 5; дефект «`Tools/audit.py` читает файлы прототипа из `Удалить/` (`prototype_coverage`)». Контракт реестра: `ТЗ_Мобильная_версия_v2.md` §3 («для каждого определения категория, ID, роль, обязательность, реализация, локализация, ресурсы и проверочный сценарий»; «неизвестный обязательный класс, атрибут или ссылка — диагностическая ошибка покрытия»; «допущение прототипа не становится подтверждением только потому, что его проверяет тест»).

## Термины
- **Симуляция** — исходники `UnityProject/Assets/Game/Scripts/Simulation/**/*.cs`.
- **Тесты** — `DotNet/**/*.cs` без `bin/` и `obj/`.
- **Запись** — элемент `definitions` в `Research/FullGame/ContentRegistry.json` (`<категория>/<ключ>`).
- **Уровни реализации** по возрастанию: `none` < `partial` < `implemented` < `verified`.

## Требования

### Т1. Разбор симуляции
1.1. КОГДА запускается аудит, СИСТЕМА ДОЛЖНА получить покрытие функцией `simulation_coverage()` только из исходников симуляции, без файлов прототипа и без `Удалить/`.
1.2. СИСТЕМА ДОЛЖНА извлечь: классы powerup из словаря `AbilityFactory`; атрибуты из `Run.SupportedHeroAttributes`; атрибуты, которые симуляция читает как `Attr.X`; условие «обработанный класс врага» из `Run.ReportUnsupportedEnemy`; обработанные движения врагов (`MovementBehavior.X` в `Run.cs`); условия реализованных подборов из `Run.Drop`; обработанные поведения спавна (`case SpawnBehavior.X` в `Run.SpawnPosition`); условия неподдержанных правил сложности из `Run.ReportUnsupportedRules`.
1.3. СИСТЕМА ДОЛЖНА сопоставлять свойства C# (`EnemyDef.AbsorbRadius`, `PickupDef.HealAmount`, …) с полями JSON по коду загрузки `GameData.cs` (`Prop = F(v, "m_…")`), а вычисляемые свойства — по их телу в `Definitions.cs`.
1.4. ЕСЛИ ожидаемая конструкция не найдена в исходниках или условие содержит свойство, которое нельзя сопоставить с данными, ТО СИСТЕМА ДОЛЖНА завершиться с ненулевым кодом и сообщением, что именно не разобрано (без молчаливого `none`).

### Т2. Поле `implementation`
2.1. КОГДА строится реестр, СИСТЕМА ДОЛЖНА записать каждой записи поле `implementation` со значением из `none`, `partial`, `implemented`, `verified` по правилам из `design.md` §3.
2.2. КОГДА у записи уровень `implemented` и ключ записи встречается строковым литералом (для атрибутов — также `Attr.<Имя>`) в тестах, СИСТЕМА ДОЛЖНА повысить уровень до `verified` и перечислить найденные тесты в поле `tests` (`Файл.cs:Метод`).
2.3. Уровень `partial` СИСТЕМА НЕ ДОЛЖНА повышать до `verified`.
2.4. СИСТЕМА ДОЛЖНА добавить в `statusValues` список `implementation`, в `summary` — счётчики `implementation:<уровень>` по категориям.

### Т3. Поле `prototype`
3.1. СИСТЕМА ДОЛЖНА СОХРАНИТЬ поле `prototype` у каждой записи с теми же значениями, что в текущем `ContentRegistry.json` (историческое покрытие прототипа), не читая исходники прототипа.

### Т4. Обязательность и роли
4.1. СИСТЕМА ДОЛЖНА записать каждой записи поле `required`.
4.2. ЕСЛИ у обязательной записи роль пустая или `unknown`, ТО СИСТЕМА ДОЛЖНА вывести список таких записей в stderr, не перезаписывать файлы реестров и завершиться с ненулевым кодом.

### Т5. Неизменное поведение
5.1. СИСТЕМА ДОЛЖНА СОХРАНИТЬ остальные поля записей, ссылки, достижимость, роли, `SoundRegistry.json` и `SourceVersions.json` в прежнем формате.
5.2. СИСТЕМА ДОЛЖНА СОХРАНИТЬ запуск `python3 Tools/audit.py [--dota PATH]` и повторяемость: два запуска подряд дают одинаковый `ContentRegistry.json`.

## Критерии приёмки
- Демо: `powerups/magic_missile` — не ниже `implemented` (см. решение Р1 в `design.md`), `powerups/echo_strike` — `none`, `enemies/absorber` — не ниже `implemented`.
- Тесты `python3 -m unittest discover -s Tools/tests` проходят, включая проверку ненулевого кода при записи без роли.
- `dotnet test DotNet/ThornThrone.Simulation.Tests` зелёный (симуляция не меняется).
- `python3 Tools/audit.py` проходит; `ContentRegistry.json` пересобран; `Mechanics.md` §1 показывает число реализованных записей.
